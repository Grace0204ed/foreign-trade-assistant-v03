# 外贸助手 V3.0 第一阶段架构审查与实施计划

日期：2026-10-24

## 一、现有架构

- 桌面框架：Electron，Windows NSIS 安装包。
- 界面：原生 HTML、CSS、JavaScript；主界面集中在 `index.html`、`app.js`，配置化工作区位于 `assets/configurable-workspaces.js`。
- 本地服务：Express，仅允许 localhost 访问。
- 数据：SQLite 保存客户、产品、报价及历史业务；公司和界面设置保存在 `company_settings.data_json`，单据正式化时保存设置与模板快照。
- PDF：使用当前单证预览 DOM 和 Electron 打印导出，预览与打印共享主要渲染内容，打印样式独立控制 A4。
- 更新：electron-updater 读取 GitHub Release 的 `latest.yml`、安装包和 blockmap。

## 二、现有业务映射

| 业务区域 | 当前主要数据来源 | V3.0 处理原则 |
| --- | --- | --- |
| 公司名称、地址、Logo、公章、签名 | 公司资料与公司配置快照 | 在公司信息统一维护，各单证选择是否引用，历史单证保留快照 |
| 报价负责人和联系方式 | 公司联系人字段 | 独立整理为报价抬头，不重复录入 |
| 银行账户与付款说明 | 银行字段列表 | 独立维护多个账户，按单证控制引用和显示 |
| 客户信息 | 客户库及当前单据 buyer 快照 | 字段可配置，当前单据可覆盖，历史保留快照 |
| 产品资料 | 产品库、产品模板、自定义值 | 产品模板独立配置；隐藏或删除字段不删除产品历史值 |
| 报价、PI、合同商品明细 | 当前单据 items 与产品模板映射 | 每种单证独立字段与布局，共用底层字段引擎 |
| 贸易、付款、运输、质保条款 | 当前模板 termFields 与当前单据 terms | 按单证独立配置，不写死到公共组件 |
| 签名、公章、背景 | 公司素材及单证显示设置 | 素材统一维护，位置、大小、显示规则由单证模板决定 |

## 三、审查发现的主要风险

1. `app.js` 仍承担较多界面、数据和渲染职责，后续应按字段引擎、素材、单证渲染和历史快照逐步拆分，不能一次性重写。
2. 旧配置中存在 `visible`、`active`、停用和输出显示等相近概念，需要迁移为“字段启用状态”和“单证输出规则”两类，迁移时保留旧值。
3. 公司资料当前以 JSON 配置为主，多公司主体、多个联系人和多个银行账户需要版本化结构及兼容迁移。
4. OCR 与自动翻译涉及外部能力；桌面离线模式必须允许人工录入，并在联网识别时先预览、人工确认，禁止直接覆盖。
5. 自由背景、多页分页和 PDF 一致性必须使用同一渲染规则逐个单证验证，不能只检查报价单。
6. 删除字段、模板和共享选项前必须检查引用关系；删除模板不能删除已有产品及历史单证数据。

## 五、数据迁移与回退原则

- 每次结构迁移使用唯一迁移键，可重复运行且不会重复破坏数据。
- 首次迁移前备份 SQLite 数据库；设置 JSON 保留旧字段并进行兼容读取。
- 新正式单证保存公司、客户、产品字段、条款、素材引用和版式快照。
- 发生同名模板或共享选项冲突时提示用户处理，不静默覆盖。
- 发布前依次执行语法检查、自动测试、实际界面检查、安装包内容检查和更新元数据检查。
